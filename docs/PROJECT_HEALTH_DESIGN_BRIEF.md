# Project Health — design brief

ТЗ для Claude Design. Задача: спроектировать страницу здоровья проекта внутри
вкладки «Проекты» дашборда MakeIT. Логика готова и работает на живых данных,
нужен качественный визуальный и информационный дизайн.

---

## 1. Контекст

MakeIT Dashboard — внутренний дашборд по портфелю из 12 проектов. Сейчас
вкладка «Проекты» = сетка карточек. По клику на кнопку «Health» в правом
верхнем углу карточки открывается страница здоровья проекта внутри той же
вкладки (не модалка, не отдельный route).

Цель страницы: куратор за 5–10 секунд видит состояние проекта по чек-листу
из 50 правил (организованных в 4 концентрических слоя) и понимает что делать.
Чек-лист — это формализация уже существующих стандартов MakeIT
(`makeit-knowledge`); правила машинно-проверяемые.

## 2. Что нужно сделать

Перепроектировать `src/components/v4/health/ProjectHealthPage.tsx` и
сопутствующие стили в `src/styles/v4.css` (секция `Project Health`).
Логика, типы и хук `useProjectHealth` остаются — менять нельзя без
согласования.

Сделать:

- **Шапку страницы** — название проекта, классификация (tier / complex / client),
  быстрый KPI-блок (Health-score + grade + тренд), кнопки «← назад» и
  «Пересканировать».
- **Health-score блок** — крупный grade (A/B/C/D/F), число 0–100, разбивка
  pass/fail/unknown по 4 слоям как stacked-bar или donut.
- **Список нарушений (fail) и предупреждений (unknown)** — главное на странице.
  Каждый item содержит: title, severity (critical/high/medium/low), detail,
  remediation-подсказку, ссылку на источник правила в makeit-knowledge,
  rule_id (моноширинно, для отладки). Должен быть быстрый скан глазами.
- **Раскрывающиеся секции pass / skipped** — показать что зелёное и что
  пропущено по applies_to (за умолчанию свёрнуто). Не отвлекают от важного,
  но дают полное покрытие.
- **Группировка по слоям** — Слой 1 Гигиена, Слой 2 Документация, Слой 3
  Свежесть и операционка, Слой 4 Drift (AI). Разбивка визуально считываема.
- **Действия по нарушениям** — пока нет реального onClick, но дизайн должен
  предусматривать кнопку «Создать issue» рядом с fail-item (логика появится
  итерацией позже, нужен placeholder).

## 3. Состояния страницы

Все состояния должны быть оформлены, не только happy path.

| Состояние | Когда | Что показать |
|---|---|---|
| **loading-initial** | Хук стартует, репорта ещё нет | Скелетон шапки + блока score + 3–5 placeholder-rows. Сообщение «Сканирую {repo}…» |
| **loading-refresh** | Репорт есть, идёт rescan | Шапка осталась, кнопка «Пересканировать» в state disabled с текстом «Сканирую…». Контент остаётся видимым (не скрывать) |
| **error** | Нет токена или GitHub отдал ошибку | Сообщение, кнопка «Попробовать снова». Не разрушать остальной layout |
| **report-clean** | Score >= 90, fails = 0 | Празднично — большой A-grade, маленький список «всё ок». Не превращать в стену зелёных галок |
| **report-issues** | Есть fails | Дефолт. Fails в топе, остальное по требованию |
| **grace-period** | Проект младше 3 дней | Бейдж «новый проект, grace 3 дня» в шапке, скрыть non-critical fails |
| **classification-missing** | Репо не в `project_classification` | Дружелюбное «Проект не зарегистрирован в Skills/PROJECT_CHECKLIST.yaml», кнопка-ссылка на репо makeit-knowledge |

## 4. Доступные данные

Структуры в `src/types/health.ts`. Главное:

```ts
HealthReport {
  repo: string;
  generated_at: ISOString;
  classification: { tier: 1|2|3, complex: boolean, client: boolean };
  in_grace_period: boolean;
  score: { raw: 0-100, grade: "A"|"B"|"C"|"D"|"F" };
  by_layer: Record<1|2|3|4, { total, pass, fail, unknown, skipped }>;
  findings: HealthFinding[];   // все правила с результатом
}

HealthFinding {
  rule_id: string;             // "hygiene.contributing"
  title: string;               // "CONTRIBUTING.md в корне"
  layer: 1 | 2 | 3 | 4;
  severity: "critical"|"high"|"medium"|"low";
  status: "pass"|"fail"|"unknown"|"skipped";
  detail?: string;             // "Нет файла CONTRIBUTING.md"
  remediation?: string;        // что делать (multi-line, иногда длинно)
  source?: string;             // "GLOBAL_CLAUDE.md (Security)"
}
```

В дополнение, из `useProjectHealth`: `loading`, `error`, `refresh()`. И
prop `project?: ProjectData` приходит снаружи с метаданными проекта
(client, phase, doneCount, openCount, velocity7d и т.д.) — можно
использовать для шапки и сайдбара.

## 5. Реальный пример данных (Beer_bot, полученный сейчас)

Для прикидки масштаба:

- 50 правил, 36 применимых (остальные skipped по applies_to)
- score 78 → grade B
- by_layer:
  - 1 (Гигиена) — 10/11 ok, 1 fail
  - 2 (Документация) — 9/11 ok
  - 3 (Свежесть/ops) — 2/9, 4 unknown, 2 fail
  - 4 (Drift AI) — 0/5, все unknown (отложено)
- 6 fails (пример первого):
  - `hygiene.contributing` — medium — «CONTRIBUTING.md в корне» — «Нет файла CONTRIBUTING.md» — remediation: «Опиши: как стартовать локально, …»
  - `tests.recent_run_green` — high — «Последний run тестов зелёный» — «CI — Lint & Test: последний run failure»
  - `ops.stale_milestones` — medium — «Нет просроченных milestones» — «Просрочено: Epic-001: Акт сверки и карточка компании»
- 9 unknown — по большей части Layer 3 freshness и Layer 4 AI-drift.

## 6. Иерархия внимания

В порядке важности (что должно быть в верхней половине экрана):

1. **Сколько надо чинить и что критично** — число fail, особенно critical/high
2. **Health-score / grade / tier** — визитка проекта
3. **Какие именно нарушения** — top-3 fails сверху по severity
4. **Тренд** — стало хуже / лучше за неделю (когда добавим — сейчас плейсхолдер)

Менее важно, но должно быть доступно:
5. Что зелёное (раскрытие секций pass)
6. Что пропущено (skipped — не применимо к этому tier'у)
7. Когда последний скан, ссылка на чек-лист в makeit-knowledge

## 7. UX-правила

- **Не превращать в дашборд KPI.** Это не метрики проекта, а аудит документации
  и гигиены. Нужно чтоб куратор видел список действий, а не графики.
- **Каждый fail-item — потенциальное действие.** Дизайн должен подразумевать,
  что у item есть «Создать issue» / «Открыть в репо» / «Открыть remediation».
- **Severity бейджи.** Critical и high должны выделяться. Medium и low —
  ненавязчивые.
- **Раскрывающиеся секции pass и skipped** — свёрнуты по умолчанию.
  Пользователь приходит на страницу за тем что не так, а не за подтверждением
  что всё ок.
- **Не дублировать данные из карточки проекта.** Бюджет / прогресс / velocity —
  пусть будут небольшим side-блоком, не главным.
- **Источник правила** — важно показать (legitimacy: «это требование из
  GLOBAL_CLAUDE.md»), но это техдетали — мелким шрифтом.

## 8. Дизайн-система

Текущая — v4 (см. `src/styles/v4.css` переменные `--v4-*`):

- `--v4-ink-*` — нейтральные тоны (50–900)
- `--v4-accent-600` — основной акцент (синий)
- `--v4-good-500/700`, `--v4-p1` — успех / опасность
- `--v4-warn-700` — предупреждение
- `--v4-mono` — моноширинный шрифт (для grade, rule_id, чисел)
- Светлая и тёмная темы (`[data-theme="dark"]`)

Не вводить новые стили без необходимости — переиспользовать `v4-panel`,
`v4-btn`, `v4-pillgrp`, `v4-tag`, существующие severity-цвета. Если нужны
новые токены — добавить наверху файла рядом с другими.

## 10. Что обязательно должно работать после редизайна

- Клик по «Health» на карточке → страница открывается без перезагрузки
- Кнопка «← Все проекты» возвращает на список
- Кнопка «Пересканировать» сбрасывает sessionStorage кэш и запускает rescan
  (в это время старый отчёт остаётся виден)
- Адаптив: страница не разваливается на ширине ≥ 1024px (мобильный — не
  приоритет, но не должно ломаться)
- Тёмная тема работает (минимум — читабельные цвета)
- Доступность: severity bage не передаёт смысл только цветом (текст должен
  оставаться)

## 11. Дальше (контекст для решений)

В следующих итерациях добавятся:
- Layer 3 проверки `doc_freshness`, `coverage_*`, `pr_touches_code_not_docs`
  (REST, без LLM)
- Layer 4 LLM-проверки (`ai_template_filled`, `ai_doc_code_sync` и т.д.) —
  будут запускаться по кнопке «Просканировать drift», результат может
  занимать 10–30 секунд
- История health-score (sparkline за 14 дней) — место под неё лучше
  заложить в шапку сейчас
- Кнопка bulk «Создать issues из всех findings» с предпросмотром

Дизайн должен оставлять пространство под эти будущие блоки, не быть
статически идеальным под текущий минимум.
