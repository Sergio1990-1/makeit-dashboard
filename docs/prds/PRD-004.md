# PRD-004: AI-инсайты на главной странице из health-движка

## Метаданные
- Статус: draft
- Автор: Sergei
- Дата: 2026-05-03
- Приоритет: P2-high
- Scope: medium (5 задач)
- Связан с: PR #131 (Project Health page, merged); `Skills/PROJECT_CHECKLIST.yaml` в `makeit-knowledge`

## Проблема
После релиза Project Health (PR #131) куратор видит реальное состояние проекта только если зашёл на его карточку → нажал «Health» → дождался скана. Главная страница до сих пор показывает 4 захардкоженных эвристики (`AIInsightsPanel`, иконки rk/gr/an/fc), которые не отражают ни реальные fails, ни триггеры из чек-листа. Это означает, что:

- Куратор не видит «что горит сегодня» в портфеле, заходя на дашборд утром.
- Сильные сигналы (`pr_doc_drift` 13 PR без правок docs, протухший `BUSINESS_PROCESS.md`, новый проект без бизнес-логики) не пробиваются в верхний слой.
- Идея пользователя из обсуждения 2026-05-02 — отслеживать **issues без milestone** на отдельной панели с графиком за 30 дней — нигде не реализована.

## Решение
Новый «портфельный» сканер: пробегает все 12 репо движком из `useProjectHealth`, агрегирует результат, выдаёт два UI-блока на главной:

1. **AIInsightsPanel** — топ-5 fail-карточек кросс-проектно, отсортированы по `severity_weights × возраст`. Каждая карточка имеет конкретное действие: «Открыть Health» или «Создать issue» (через эпик B, см. PRD-005). Сейчас — открытие Health-страницы; кнопка «Создать issue» появится после Epic-006.
2. **OrphanIssuesPanel** — тонкая панель с графиком: число issues без milestone по дням за последние 30 дней (агрегат по всему портфелю + drill-down по проектам в тултипе). Аналог `ClosedChart30d`.

Сканирование триггерится:
- На первое открытие дашборда (если кэш истёк > 30 минут или его нет).
- По нажатию существующей кнопки «Обновить» в шапке.
- Не на каждом рендере — иначе REST GitHub API убьёт rate limit.

Кэш — `localStorage`, key `makeit_portfolio_health_v1`, TTL 30 минут. На странице видно `обновлено N мин назад`, спинер при scan.

## Пользователи и роли
| Роль | Что делает | Ключевые потребности |
|------|-----------|---------------------|
| Куратор портфеля | Утром заходит на дашборд, видит «что критично сегодня» | Топ-N карточек с действием в один клик |
| Разработчик MakeIT | Видит сводный сигнал по всем своим проектам | Куда смотреть в первую очередь |

N/A — фронтенд-only, без транзакций/денег/состояний. Источник истины — GitHub API (live data), кэш — производный.

## Функциональные требования
| ID | Требование | Приоритет |
|----|-----------|-----------|
| FR-1 | При первом заходе на дашборд (или TTL > 30 мин) запускается портфельный скан всех 12 репо параллельно (concurrency=3 одновременно работающих репо, чтобы не выжечь rate limit) | must |
| FR-2 | `AIInsightsPanel` показывает топ-5 fail-findings из всего портфеля, отсортированных по `severity_weights × age_factor`. age_factor = 1 + min(7, days_since_first_seen)/7 (свежие весомее, насыщение к 7 дням) | must |
| FR-3 | Каждая карточка инсайта содержит: repo, layer, severity, title, detail; кнопку «Открыть Health» (переключает вкладку Проекты + selectedRepo) | must |
| FR-4 | Кнопка «Создать issue» на карточке инсайта появляется после Epic-006 (PRD-005). Сейчас — заглушка с tooltip «доступно после Epic-006» | should |
| FR-5 | `OrphanIssuesPanel` — компонент с графиком количества open-issues без milestone по дням за 30 дней, агрегат по портфелю. Использует API `listIssuesWithoutMilestone` (уже есть в github-actions.ts) + `created_at` каждого issue для бакетирования | must |
| FR-6 | Кэш в localStorage `makeit_portfolio_health_v1`, TTL 30 минут, инвалидация по кнопке «Обновить» в шапке (event bus или callback prop) | must |
| FR-7 | При неполном скане (например, токена нет на половине repo, rate limit на shields.io) — частичный результат показывается, отсутствующие данные помечены `?` | should |
| FR-8 | На дашборде badge у пункта «Дашборд» в sidebar с числом критичных fails в портфеле (если их ≥ 1) — `red dot + count` | nice |

## Нефункциональные требования
- **Производительность**: полный скан 12 репо ≤ 60 секунд при тёплом кэше веток. Portfolio scan не должен блокировать рендер дашборда — стартует фоном после mount.
- **Rate-limit safety**: max 3 одновременно сканируемых repo (3 × ~50 запросов = 150 в окне). Учитывая существующий `useDashboard` (1 GraphQL запрос на старт), не пересекаем 5000/час.
- **Идемпотентность**: повторный скан того же snapshot tree-sha не должен порождать новых entries в localStorage trend (уже соблюдается в `health-engine.ts:appendTrendPoint`).

## Влияние на существующий функционал
| Что | Риск |
|---|---|
| `AIInsightsPanel.tsx` | Полностью переписан, prop-API заменяется |
| `App.tsx` / `DashboardView.tsx` | Добавляется portfolio-scan хук + проброс данных в AIInsightsPanel и OrphanIssuesPanel |
| `useProjectHealth.ts` | Не меняется — переиспользуется его внутренности через новый хук `usePortfolioHealth` |
| Sidebar.tsx (главная навигация) | Возможен новый badge с числом критичных fails — изменение только разметки/CSS |
| Кнопка «Обновить» в Topbar | Должна теперь триггерить и portfolio-rescan, не только базовый `useDashboard.refetch` |

Регрессии:
- Дашборд может стать тяжелее на старте — mitigation: portfolio scan стартует через 1.5 секунды после mount, чтобы не мешать первому painted.
- Если GitHub отдаст 403 на половине проектов — UI должен корректно показать частичный результат (FR-7).

## Критерии приёмки
- [ ] При открытии вкладки «Дашборд» через ≤ 60 секунд появляется список из ≤ 5 карточек инсайтов с реальными данными (не заглушки).
- [ ] Клик «Открыть Health» на карточке инсайта переключает вкладку «Проекты» + открывает страницу health для нужного repo.
- [ ] Панель orphan-issues показывает график за 30 дней с правильным значением «сейчас» (`listIssuesWithoutMilestone` для каждого репо, сложить).
- [ ] Кнопка «Обновить» в Topbar инвалидирует и базовый кэш, и portfolio-кэш.
- [ ] При sessionStorage переполнении (искусственно) UI не падает — продолжает работать без кэша.

## Открытые вопросы
- [ ] **(уточнить с пользователем)** Сколько карточек показывать на дашборде — фиксированно 5 или адаптивно в зависимости от `severity` (например все critical + top high до общего лимита 8)? **Решение по умолчанию**: фиксированно 5, показывать в порядке `critical → high → medium`, в одном severity — по `weight × age_factor`.
- [ ] **(уточнить)** Куда деваются «дубли» — если у двух проектов одинаковая ошибка `hygiene.contributing` fail — это две карточки или одна сводная? **Решение по умолчанию**: две карточки (один rule в одном проекте = одна карточка).
