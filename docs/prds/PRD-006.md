# PRD-006: Layer 4 — LLM-проверки drift'а в Project Health

## Метаданные
- Статус: draft
- Автор: Sergei
- Дата: 2026-05-03
- Приоритет: P3-medium
- Scope: large (7 задач)
- Связан с: PR #131 (Project Health — Layer 4 правила сейчас возвращают `unknown`); `Skills/PROJECT_CHECKLIST.yaml`

## Проблема
В `PROJECT_CHECKLIST.yaml` есть 7 правил уровня 4 (LLM-проверки drift):

| rule_id | Что должна проверять | Сейчас |
|---|---|---|
| `client.contract_stages_filled` | CONTRACT_STAGES.md заполнен (не плейсхолдеры `[Название]`) | unknown |
| `drift.brief_template_filled` | BRIEF/SPEC в `docs/prds/` заполнены, не пустые шаблоны | unknown |
| `client.contract_milestones_sync` / `drift.contract_milestones` | Этапы CONTRACT_STAGES соответствуют GitHub milestones | unknown |
| `drift.state_machines_vs_code` | STATE_MACHINES.md ↔ enum статусов в моделях / FSM в коде | unknown |
| `drift.knowledge_coverage` | knowledge/{repo}.md покрывает все домены кода | unknown |
| `drift.claude_md_freshness` | пути и команды в CLAUDE.md ещё валидны | unknown |

Результат: на странице Health у tier-1 complex проектов (mankassa, Sewing-ERP) колонка Layer 4 — все unknown. Самое ценное (drift между документацией и кодом) недоступно.

При этом запускать LLM-проверки на каждом обычном скане — дорого (5–20 секунд + $$). Нужна отдельная кнопка «Просканировать drift», которая уже есть в дизайне `Hero` как no-op.

## Решение
Запускать Layer 4 проверки **только по кнопке** «Просканировать drift». Результат:

1. Отдельный path в health-engine: `runDriftScan(token, owner, repo, doc, claudeKey)` — проходит правила Layer 4, для каждого формирует prompt из `evidence` (миграции/модели/FSM/доки), отправляет в Claude API, парсит structured response.
2. Кэш по **tree-sha** репо (`HEAD` дерева через `GET /repos/.../git/trees/main`). Если sha не изменилась с прошлого drift-скана — берём из кэша. localStorage key: `makeit_drift_cache:{repo}:{tree_sha}`.
3. Результат drift-скана мерджится в `report.findings`, заменяя соответствующие `unknown` на `pass`/`fail` с detail и remediation.
4. UI: кнопка `Hero` — disabled во время скана + индикатор прогресса («2/7 правил…»). После — toast «drift-скан завершён, +N fails».
5. Модель: `claude-haiku-4-5` для большинства правил (дешёвая, быстрая); `claude-opus-4-7` для `drift.state_machines_vs_code` и `drift.knowledge_coverage` — сложные семантические сравнения.

Для каждого правила — свой `evidence collector` + `prompt template`:

- **`ai_template_filled`**: читаем file → ищем плейсхолдеры `[\\w\\s]+\\]`, `XXX`, `TODO` count → если > threshold, фейл. **Без LLM** для этой подзадачи (regex достаточно). Помещаем в Layer 4 ради тематической группировки, но реализуется как extra check без Claude.
- **`ai_contract_milestones_sync`**: read `docs/CONTRACT_STAGES.md` + `listMilestones`. Prompt: «вот этапы контракта, вот milestones — какие расходятся? structured JSON output».
- **`ai_doc_code_sync`** (state_machines): read `docs/STATE_MACHINES.md` + grep для enum статусов в `app/models/` (через Code Search API). Prompt: «вот описание FSM в доке, вот найденные статусы в коде, что не совпадает?».
- **`ai_knowledge_coverage`**: read `knowledge/{repo}.md` + список доменов из `docs/DOMAINS/`. Prompt: «вот описание бизнес-логики, вот домены кода — какие домены не упомянуты?».
- **`ai_claude_md_freshness`**: read `CLAUDE.md` + `listRepoFiles('.')`. Prompt: «найди в CLAUDE.md упоминания путей/файлов/команд, проверь существуют ли они».

Все промпты возвращают structured JSON через Anthropic tool use:

```json
{
  "status": "pass" | "fail",
  "detail": "<= 200 chars, plain text>",
  "remediation": "<= 400 chars, plain text>",
  "confidence": 0.0..1.0
}
```

Если confidence < 0.7 — статус `unknown` с пометкой «низкая уверенность».

## Пользователи и роли
| Роль | Что делает | Ключевые потребности |
|------|-----------|---------------------|
| Куратор сложного проекта | Раз в неделю запускает drift-скан | Узнать что код ушёл вперёд, а доки устарели — без ручного аудита |
| Maintainer client-проекта | Перед демо клиенту проверяет CONTRACT_STAGES sync | Убедиться что описание этапов в репо ↔ milestones |

## Функциональные требования
| ID | Требование | Приоритет |
|----|-----------|-----------|
| FR-1 | Кнопка «Просканировать drift» в Hero становится active при наличии Claude API key (хранится в localStorage `claude_api_key`, уже есть в `config.ts`) | must |
| FR-2 | Запуск drift-скана: для каждого Layer 4 правила собрать evidence, послать в Claude API, спарсить ответ. Concurrency = 2 (чтобы не выжечь Anthropic rate limit) | must |
| FR-3 | Кэш по tree-sha: перед каждым правилом проверка `localStorage.getItem('makeit_drift_cache:'+repo+':'+sha+':'+rule_id)`. Hit → не дёргать LLM. TTL — нет, кэш живёт пока tree-sha та же | must |
| FR-4 | Прогресс-бар во время скана: «{done}/{total} правил». После — toast «drift-скан завершён, нашёл +N fails, X cached» | must |
| FR-5 | `ai_template_filled` реализуется без LLM: regex-detector плейсхолдеров (`\[(?:Название|YYYY-MM-DD|сумма|номер)[^\]]*\]`, `XXX`, `TODO`). Если найдено > 5 — fail | must |
| FR-6 | `ai_contract_milestones_sync`: читать docs/CONTRACT_STAGES.md, listMilestones, отправить в Claude haiku, спарсить structured output | must |
| FR-7 | `ai_doc_code_sync` (`drift.state_machines_vs_code`): читать docs/STATE_MACHINES.md + Code Search для enum status (через `searchCodeSymbol`) — отправить в Claude opus | must |
| FR-8 | `ai_knowledge_coverage`: читать `knowledge/{repo}.md` (с учётом `knowledge_path` override) + listRepoFiles('docs/DOMAINS') — отправить в Claude opus | should |
| FR-9 | `ai_claude_md_freshness`: читать CLAUDE.md + listRepoFiles корня — отправить в Claude haiku | should |
| FR-10 | Структурированный вывод через Anthropic tool use (один tool `report_finding` с полями status/detail/remediation/confidence) | must |
| FR-11 | confidence < 0.7 → status `unknown`, detail помечается префиксом `(уверенность {pct}%) …` | must |
| FR-12 | После drift-скана отчёт обновляется в sessionStorage кэше (тот же ключ что и обычный health-отчёт) — с пометкой `drift_scanned_at` в HealthReport | must |

## Нефункциональные требования
- **Стоимость**: один drift-скан репо ≤ $0.05 (haiku для 4 правил, opus для 2 — суммарно ≈ 30k input + 1k output токенов = $0.045 при текущих ценах).
- **Латентность**: ≤ 30 секунд для tier-1 complex репо (5–7 правил, concurrency=2).
- **Отсутствие Claude key**: кнопка просто disabled с tooltip «нужен Claude API key — настройка в шапке».
- **Privacy**: код проектов отправляется в Anthropic API. Это документируется в `docs/SECURITY.md` (нужно создать) и упоминается в tooltip кнопки drift-скана при первом запуске.

## Влияние на существующий функционал
| Что | Риск |
|---|---|
| `health-engine.ts` | Новая функция `runDriftScan`, не меняет существующие executor'ы (Layer 4 cases уже возвращают unknown — после реализации возвращают реальный результат) |
| `useProjectHealth.ts` | Новый метод `scanDrift()`, новое поле `driftScanning: boolean` в state |
| `ProjectHealthPage.tsx` / `Hero.tsx` | Кнопка drift из no-op в активную, прогресс-бар |
| `claude.ts` (utils) | Может понадобиться `callClaudeWithTool(prompt, toolDef, model)` хелпер — структурированный output |
| `config.ts` | Уже есть `getClaudeKey/setClaudeKey` — переиспользуем |

Регрессии:
- Если структурированный output Claude когда-нибудь вернёт неожиданный формат — fail-safe в `unknown`, не крэшим страницу.
- Tree-sha кэш может «застрять» если репо переименован или ветка по умолчанию сменилась — mitigation: при load репо запоминать default_branch (через `getRepoMeta`), кэш-ключ включает branch.
